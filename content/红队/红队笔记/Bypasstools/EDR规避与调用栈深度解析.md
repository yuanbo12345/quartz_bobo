# EDR规避技术与调用栈深度解析

***

**免责声明：** 此处讨论的所有技术仅用于学术研究、安全防御和授权测试目的。滥用这些技术从事非法攻击活动将承担严重的法律后果。了解攻击者的手段是构建更强大防御体系的关键。

## Part 1: 宏观层面：现代EDR规避技术的通用策略

近两年，攻击技术已经从简单的文件混淆、加壳，演变为一场围绕**“EDR传感器”**的攻防战。EDR的核心是其部署在端点上的传感器（Sensor），这些传感器通过各种机制监控系统行为。因此，最高级的规避技术都旨在**致盲、欺骗或绕过**这些传感器。

以下是几种最主流且高效的技术：

### 1. 直接系统调用 (Direct Syscalls) & 间接系统调用 (Indirect Syscalls)

*   **技术简介**：传统API调用（如 `CreateRemoteThread`）会经过多个层次，如 `kernel32.dll` -> `ntdll.dll`，而EDR通常在 `ntdll.dll` 这一层对敏感函数进行挂钩（Hooking），以监控API调用。直接系统调用则是完全绕过这些被挂钩的DLL，直接通过汇编指令（如 `syscall`）进入内核，执行操作。间接系统调用则是通过寻找未被挂钩的、但最终会发出相同 `syscall` 指令的“干净”代码片段来执行，更具隐蔽性。

*   **技术原理**：**规避用户层API挂钩 (User-Mode API Hooking)**。EDR在用户空间的主要监控手段就是在 `ntdll.dll` 中放置“探针”（JMP指令跳转到EDR的分析引擎）。通过直接构造系统调用号（SSN）和参数，攻击代码可以像操作系统自身一样与内核直接对话，EDR的用户层探针就完全看不到这次调用。这使得EDR无法通过API监控来发现恶意行为，例如进程注入、内存修改等。

### 2. 自带脆弱驱动 (Bring Your Own Vulnerable Driver - BYOVD)

*   **技术简介**：这是目前最强大、最流行的技术之一。攻击者将一个合法的、但存在已知漏洞的第三方驱动程序（例如，来自游戏反作弊、硬件工具的驱动）打包到恶意软件中。在目标系统上，他们首先加载这个合法的、有签名的驱动，然后利用其漏洞，获得内核级别的任意代码执行或任意地址读写权限。

*   **技术原理**：**实现权限提升至内核态 (Ring 0)**。一旦获得内核权限，攻击者就拥有了与EDR内核驱动同等级别甚至更高的权限。他们可以做到：
    *   **卸载或禁用EDR驱动**：直接终止EDR的核心防护。
    *   **移除EDR内核回调**：见第二部分的详细解释。
    *   **直接操作内核对象**：隐藏进程、线程、网络连接等。
    *   这种方法极其有效，因为它利用的是“受信任的”驱动程序，许多安全产品的信任模型会被打破。

### 3. ETW (Event Tracing for Windows) 补丁与篡改

*   **技术简介**：现代EDR，特别是微软自家的Defender for Endpoint和CrowdStrike，严重依赖ETW来获取系统活动的详细遥测数据（如进程创建、网络请求、注册表访问等）。攻击者通过定位并修补（Patch）内核中负责分发ETW事件的关键函数（如 `nt!EtwpTraceEvent`），使其直接返回或跳过事件发送，从而让EDR接收不到任何有价值的日志。

*   **技术原理**：**切断EDR的信息来源**。ETW是Windows内核提供的一个高性能、低开销的日志系统。通过篡改ETW的事件分发机制，攻击者相当于剪断了EDR的“电话线”。EDR本身可能还在正常运行，但它已经变成了一个“聋子”，对系统上发生的绝大多数恶意行为一无所知。

### 4. 进程伪装与掏空 (Process Herpaderping & Process Doppelgänging)

*   **技术简介**：这些技术利用了Windows加载进程时“文件锁定”与“内存映射”之间的时间差。
    *   **Herpaderping**：先创建一个文件，写入恶意代码，然后获取该文件的句柄。接着，用无害内容覆盖原始文件。最后，利用之前获取的句柄创建进程。EDR去检查磁盘上的文件时，看到的是无害内容，但实际运行在内存中的是之前的恶意代码。
    *   **Doppelgänging**：利用事务性NTFS（TxF）API，创建一个事务，在事务中写入恶意文件，然后基于这个文件创建内存Section并加载进程。在进程启动前，回滚该事务。最终效果是，进程从一个“从未在磁盘上存在过”的文件启动，EDR无法进行基于文件的静态扫描。

*   **技术原理**：**欺骗基于文件的静态和动态检测**。EDR通常会在进程创建时扫描其对应的磁盘文件。这些技术的核心思想是让“磁盘上的映像”与“内存中的映像”不一致，从而绕过EDR的扫描和启发式分析。

## Part 2: Shellcode+Loader 如何规避内核层检测

当谈到像CrowdStrike这样的顶级EDR时，它们的核心优势在于其强大的**内核层传感器**。仅仅使用用户层的直接系统调用是不够的，因为EDR在内核中依然能看到进程/线程的创建、内存的分配等。要做到“完全规避”，Loader必须有能力对抗内核层的监控。

这通常是通过前面提到的 **BYOVD** 技术获得内核权限后，由Shellcode或Loader执行以下操作：

### 1. 移除内核回调 (Kernel Callback Removal)

*   **技术简介**：Windows内核允许驱动程序注册“回调例程”（Callback Routines），以便在特定事件发生时收到通知。例如 `PsSetCreateProcessNotifyRoutine`（进程创建/退出时通知）和 `PsSetCreateThreadNotifyRoutine`（线程创建/退出时通知）。EDR的核心就是注册这些回调来监控系统。攻击者获得内核权限后，会遍历内核中的这些回调函数数组（如 `PspCreateProcessNotifyRoutine`），找到并移除属于EDR驱动的回调指针。

*   **技术原理**：**直接致盲EDR的内核“眼睛”**。移除了回调，就等于让EDR的内核驱动再也无法收到关于进程/线程活动的通知。当你的Loader后续再进行进程注入、创建新线程来执行核心Shellcode时，EDR的内核传感器对此一无所知，因为它根本没有收到内核的“事件通知”。这是最直接、最有效的规避方式，但风险也很高，操作不当会导致系统蓝屏（BSOD）。

### 2. 直接内核对象操作 (Direct Kernel Object Manipulation)

*   **技术简介**：在内核中，每一个进程都由一个 `EPROCESS` 结构体表示，它们通过一个双向链表（`ActiveProcessLinks`）连接在一起。获得内核权限后，攻击代码可以找到自己进程的 `EPROCESS` 结构，并将其从这个链表中“摘除”（`LIST_ENTRY` 指针断链）。

*   **技术原理**：**实现进程的深度隐藏**。一个从 `ActiveProcessLinks` 链表中摘除的进程，对于所有依赖这个链表来枚举进程的程序（包括任务管理器、Process Explorer以及EDR的进程列表查询功能）来说，都是不可见的。虽然EDR可能通过回调捕获到了进程的初始创建，但当它想进一步检查这个进程时，却发现它“消失”了，从而中断了分析链。

### 3. 线程调用栈欺骗 (Call Stack Spoofing)

*   **技术简介**：EDR在检测到可疑线程时，会检查其调用栈。一个从非模块支持的内存（`MEM_PRIVATE`）或读写执行（RWX）内存区域启动的线程，其调用栈会非常可疑。高级的Loader会在执行Shellcode前，精心伪造一个“合法”的调用栈。例如，它会修改栈帧，使其看起来像是从一个正常的系统DLL（如 `ntdll.dll` 或 `wininet.dll`）中的合法函数调用而来，而不是从一块刚分配的内存启动。

*   **技术原理**：**符合EDR的“行为基线”**。EDR依赖启发式规则来判断线程行为是否正常。一个干净、合法的调用栈可以极大地降低线程的“可疑评分”。这使得即使EDR看到了线程的创建（假如内核回调未被移除），它在分析调用栈时也可能认为这是一个正常操作，从而放行。

### 4. 硬件断点与异常处理 (Hardware Breakpoints & Exception Handling)

*   **技术简介**：这是一种更隐蔽的执行流程控制方法。Loader可以设置硬件断点（比软件断点更难被检测），然后故意触发它。接着，它会注册一个自己的异常处理器（Vectored Exception Handler），在异常处理器中执行核心的Shellcode。

*   **技术原理**：**劫持系统正常的异常处理流程**。EDR很难区分这是一个恶意的、用于执行代码的异常，还是一个程序运行中正常的意外。通过这种方式，可以将执行流无缝地转移到恶意代码中，而表面上看起来只是一次普通的硬件异常事件，从而绕过基于API调用序列的检测逻辑。

### 总结：完整攻击链

要实现对CrowdStrike这类高级EDR的完全规避，一个现代的`Shellcode+Loader`组合拳通常是这样：

1.  **入口 (Initial Execution)**：通过钓鱼、漏洞利用等方式，执行初始Loader。
2.  **提权 (Privilege Escalation)**：Loader利用 **BYOVD** 技术，加载一个有漏洞的合法驱动，从而获得内核读写权限。
3.  **致盲 (Blind the EDR)**：获得内核权限后，立即执行最关键的操作：
    *   **移除EDR的内核回调**，使其无法监控后续的进程/线程活动。
    *   **篡改ETW**，切断EDR的另一大信息来源。
4.  **执行 (Execution)**：在EDR被“致盲”后，Loader才开始执行真正的恶意操作，例如：
    *   使用**直接系统调用**进行进程注入（如注入`lsass.exe`）。
    *   创建新线程执行核心功能的Shellcode，并可能使用**调用栈欺骗**技术使其看起来更合法。
5.  **隐藏 (Hiding)**：通过**直接操作内核对象**（如断开`EPROCESS`链表），将自身进程彻底隐藏。

这是一个完整且高度对抗性的攻击链，每一步都针对EDR的不同检测层（静态、用户层、内核层）进行精确打击。

## Part 3: 调用栈分析与运行时欺骗

### 3.1 BOF执行期间的调用栈变化

当你已经完成了合法的堆栈欺骗，让Loader在“休眠”时看起来无害，但在执行一个BOF（Beacon Object File）时，这个“伪装”会被暂时打破。

**场景设定:**

1.  **你的Loader**：已经成功运行，并伪装成了 `wininet.dll` 在调用 `NtWaitForSingleObject`。
2.  **你的BOF**：一个简单的BOF，功能是执行 `whoami`。
3.  **内存区域**：
    *   `wininet.dll`: 合法的、有签名的系统模块。
    *   `Loader.dll` (或内存区域): 你的Loader代码所在的位置，是 `MEM_PRIVATE`。
    *   `BOF.bin` (或内存区域): 为BOF分配的新的可执行内存，同样是 `MEM_PRIVATE`。

#### 第一阶段：上线休眠时 (Spoofed Idle State)

EDR检查这个线程时，看到的调用栈如下：

**图1：欺骗后的休眠调用栈**
```
(高地址 - 栈底)
+-----------------------------------------+
| ntdll!RtlUserThreadStart                |
+-----------------------------------------+
| kernel32!BaseThreadInitThunk            |
+-----------------------------------------+
| wininet!InternetOpenW                   |  <-- [SPOOFED] 伪造的返回地址
+-----------------------------------------+
| wininet!HttpSendRequestW                |  <-- [SPOOFED] 伪造的返回地址
+-----------------------------------------+
| ntdll!NtWaitForSingleObject             |
+-----------------------------------------+
| Loader_Sleep_Function()                 |
+-----------------------------------------+
(低地址 - 栈顶)
```
**分析**：这个调用栈非常“干净”，看起来完全正常。欺骗的核心在于，`Loader_Sleep_Function` 的返回地址被修改，指向了 `wininet.dll` 内部，而不是Loader自己的代码。

#### 第二阶段：执行BOF时 (The Moment of Truth)

当Loader唤醒并调用BOF的入口点（`bof_go`）时，调用栈发生了根本性的变化。

**图2：执行BOF内部API时的调用栈**
```
(高地址 - 栈底)
+-----------------------------------------+
| ntdll!RtlUserThreadStart                |
+-----------------------------------------+
| kernel32!BaseThreadInitThunk            |
+-----------------------------------------+
| wininet!InternetOpenW                   |
+-----------------------------------------+
| wininet!HttpSendRequestW                |  <-- 伪造的栈帧依然存在
+-----------------------------------------+
| Loader_Main_Loop()                      |  <-- Loader从休眠返回，调用BOF
+-----------------------------------------+
| bof_go()                                |  <-- !!! 关键转折点 !!!
+-----------------------------------------+
| kernelbase!CreateProcessW               |  <-- BOF调用的API
+-----------------------------------------+
| ntdll!NtCreateUserProcess               |
+-----------------------------------------+
(低地址 - 栈顶)
```

**分析与核心风险点：**
伪装被“顶破”了。新的、真实的调用帧被压在了旧的、欺骗性的帧之上。EDR会看到一个致命的转换：一个合法的、有签名的模块（`wininet.dll`）的执行流，最终返回到了一个**没有任何文件支持的私有内存区域** (`Loader_Main_Loop`)。

> **EDR核心检测逻辑之一**: "一个线程的调用栈显示其执行流从一个有签名的、磁盘上的模块，直接跳转到了一个没有文件支持的可执行内存中。"

这是一个极度可疑的模式，会立即触发警报。

### 3.2 如何看懂调用栈 (以WinDbg为例)

**核心原则：调用栈是“倒序”的，最上面的是最新的，最下面的是最旧的。**

**WinDbg示例 (`k`命令):**
```
Child-SP         RetAddr          Call Site
00000080`f9f7d878 00007ff8`a2b3c5a9 ntdll!NtReadFile+0x14
00000080`f9f7d880 00007ff8`a011e8c8 KERNELBASE!ReadFile+0x79
00000080`f9f7d920 00007ff7`b3e412b3 MyProgram!ProcessData+0x158
00000080`f9f7d9f0 00007ff7`b3e410ad MyProgram!main+0x83
00000080`f9f7da30 00007ff8`a38a7344 MyProgram!__scrt_common_main_seh+0x10d
00000080`f9f7da70 00007ff8`a4e226b1 kernel32!BaseThreadInitThunk+0x14
00000080`f9f7daa0 00000000`00000000 ntdll!RtlUserThreadStart+0x21
```
**解读顺序（从下往上看）：**
`RtlUserThreadStart` -> `BaseThreadInitThunk` -> ... -> `main` -> `ProcessData` -> `ReadFile` -> `NtReadFile`。当前执行点在最顶端的 `NtReadFile`。

**用户层与内核层：**
调用栈是统一的、按时间顺序的列表，它会无缝地跨越用户层和内核层的边界。WinDbg等工具会自动将用户栈和内核栈“拼接”起来，形成一个完整的调用历史。

**其他查看工具：**
1.  **Process Hacker**: 强大的任务管理器替代品，可轻松查看线程堆栈。
2.  **Process Explorer (Sysinternals Suite)**: 微软官方经典工具。
3.  **Visual Studio Debugger**: 开发时的最佳选择。
4.  **x64dbg / OllyDbg**: 偏向逆向工程的调试器。

### 3.3 运行时调用栈欺骗 (On-the-fly Call Stack Spoofing)

为了解决BOF执行期间的暴露问题，可以在调用敏感API前，再次主动伪造调用栈。

**核心目标**：在调用 `CreateProcessW` 的那一刻，让 `Loader_Main_Loop` 和 `bof_go` 从调用栈中彻底消失。

**技术实现步骤：**

1.  **寻找“跳板”(Gadget)**：在 `ntdll.dll` 等合法模块中找到一个 `ret` 指令（汇编 `C3`）的地址。
2.  **准备调用**：在BOF代码中，`call CreateProcessW` 之前：
    a.  保存真实的返回地址（指向 `Loader_Main_Loop`）。
    b.  将找到的 `ntdll!ret` 的地址压入栈中，作为伪造的返回地址。
3.  **调用API**：执行 `call CreateProcessW`。
4.  **EDR检查**：此时EDR看到的调用栈，`CreateProcessW` 的调用者地址是 `ntdll!ret`，它会认为是一个合法的 `ntdll.dll` 在发起调用，欺骗成功。
5.  **清理恢复**：`CreateProcessW` 返回后，BOF代码需要恢复栈，并将真实的返回地址放回栈上，以便能正确返回到Loader的主循环。

## Part 4: 自定义函数在调用栈中的显示

### 1. 自定义函数会显示吗？

**会的，绝对会。** 调用堆栈会记录所有函数调用，包括你自己写的。

### 2. 如何显示？（关键在于符号）

函数名如何显示，完全取决于调试器或EDR能否找到**符号文件（PDB）**。PDB文件是编译器生成的“字典”，用于将内存地址翻译成函数名、变量名等。

#### 情况一：有符号文件（开发者场景）

如果PDB文件存在，调用堆栈会清晰地显示你的自定义函数名。
```
MyProgram!MyCustomFunctionB+0x2a  <-- 名字被成功解析!
MyProgram!MyCustomFunctionA+0x1f  <-- 名字被成功解析!
MyProgram!main+0x15               <-- 名字被成功解析!
```

#### 情况二：无符号文件（恶意软件/Shellcode场景）

**子情况 A：代码在模块内，但无符号**
如果代码在你的EXE里，但没有PDB文件，会显示为 **`模块名 + 偏移量`**。
```
MyProgram+0x1337                  <-- 无法解析！
MyProgram+0x12f0                  <-- 无法解析！
```

**子情况 B：代码在匿名内存中（Shellcode）**
如果代码在 `VirtualAlloc` 申请的匿名内存中，这块内存不属于任何模块。当EDR或调试器试图解析调用地址时，查询会完全失败。

此时，调用堆栈会显示为一个 **纯粹的、未解析的内存地址**。
```
kernelbase!CreateProcessW+0x79
0x000001A4`12345678               <-- !!! 致命的红灯：一个原始内存地址 !!!
```
**这对EDR来说，是一个极其强烈的危险信号（IOC）。** 它意味着一个合法的API，其调用者竟然是一个没有任何身份的匿名内存地址，这几乎可以断定是恶意的无文件攻击。
